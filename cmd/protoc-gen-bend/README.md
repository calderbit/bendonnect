# protoc-gen-bend

A protoc / buf plugin that generates Bend 2 code for Bendonnect from proto3 files.

**Beta:** the generated API may change between 0.x releases.

    go install github.com/calderbit/bendonnect/cmd/protoc-gen-bend@latest
    # or, from a checkout: cd cmd/protoc-gen-bend && go build -o bin/protoc-gen-bend .

```yaml
# buf.gen.yaml
version: v2
plugins:
  - local: path/to/protoc-gen-bend
    out: gen
    opt:
      - runtime=../..   # path from the output directory to the Bendonnect root (required)
```

`runtime` may instead name the BendHub package (`runtime=bendonnect@0.1.0.0`, or a `0x<hash>`);
hub names are written into the imports verbatim, without the relative-path adjustment.

For `greet.proto` it writes `greet_pb.bend` (messages and codecs, pure: `bend greet_pb.bend`
prints ALL PROOFS CHECK) and, when the file has services, `greet_connect.bend` (server handler,
client functions). The files are `_pb` / `_connect` and not `.pb.bend` / `.connect.bend` because
Bend refuses to import a module whose name has a dot. Output is deterministic and starts with
`# Code generated by protoc-gen-bend. DO NOT EDIT.` and the `# source:` path. Imports use the
`runtime` path (plus one `..` per directory level of the proto path) for `src/pb.bend` (Pbr),
`src/pbjson.bend` (Pj), `src/transport/rpc.bend` (Rpc) and the rest of the core.

## What is generated

Value mapping is in `src/README-codegen.md`. For a message `M` (nested: `Outer.Inner`):
`M.default()`, `M.encode_proto/decode_proto`, `M.to_json/from_json/encode_json/decode_json`,
`M.encode(+codec, m)`, `M.decode(+codec, b)`; enums: `E.<VALUE>()`, `E.name(+n)` ("" when
unknown), `E.from_name(+s)`; oneofs: sum type `M.<Oneof>` with `M.<Oneof>.None{}`; map fields: an
entry type `M.<Field>Entry{key, value}` (message values are stored directly, not in a Maybe).
Service `S`: `S.owns(+procedure)`, `S.<Method>.procedure()`, `S.handle(~impl.., call)`,
`S.<Method>.send(out, msg)` (server streams), client `S.<snake_method>(base_url, +codec,
headers, req)` and `S.<snake_method>_get` for `NO_SIDE_EFFECTS` unary methods. Bidi methods:
the server answers Unimplemented and there is no client function.

Proto binary is written in field-number order (maps as given, one entry message each, key and
value always present like protobuf-go); unknown fields are dropped on decode; packed and
unpacked repeated numerics are both read. JSON follows the proto3 mapping through `Pj`.

Names: Bend keywords (`type match case def law for exs import as is do return where Kind Type
Data`) get a trailing `_`; so do top-level messages named like a Base type/constructor or like
a module alias the generated files use (`Empty`, `Event`, `List`, `Result`, `Code`, `E`, ...), e.g.
message `Event` is `Event_`.

## Recursion

Bend forbids mutual recursion, and requires structural decrease. A message that contains itself
(directly, in a repeated field, or in a oneof member) is generated as one recursive def per
direction whose first argument is a depth counter (limit 100 levels, the same limit rejects
deeper input on decode; on encode, anything deeper than 100 levels is dropped). Everything else
is plain structural code.

## Not supported in v1 (clear generator errors)

- proto2 and editions files; groups; public/weak imports.
- Messages that are mutually recursive (A contains B contains A), and a map whose value type
  contains the enclosing message (`map<string, Tree>` inside `Tree`).
- Well-known types have no special JSON mapping (generate `google/protobuf/*.proto` with the
  plugin if you need them as plain messages).
- `double` is held as `F32` (lossy), as per the contract.
- Cross-file imports: each imported file that declares anything must itself be generated
  (same buf run); it is imported as `<package>_<file stem>` (dots become `_`) and its types
  are used qualified. Two imports that map to the same alias are an error.
- Streaming: client/server streams use the HTTP/1.1 transport (buffered request messages).
